# Full tmux recording

Termtrace can record a tmux session at two levels:

- a composite client track containing the full screen a tmux client presented,
  including pane borders, status lines, layout, zoom, copy mode, prompts, and
  active-pane changes;
- individual pane tracks containing clean canonical PTY evidence and semantic
  state for each recorded pane.

The composite track is the faithful video source. Pane tracks support
pane-specific inspection and command provenance. An aggregate manifest links
the composite session, pane recordings, stable tmux identities, lifecycle and
layout observations, and any coverage gaps.

## Record a complete tmux workflow

```sh
termtrace tmux record work --new -- tmux new-session -s work
termtrace tmux status work
termtrace tmux stop work --wait
termtrace tmux video work --out work.mp4 --preset docs
```

`record` runs the exact trailing tmux client command as the composite track and
configures pane recording for the same aggregate. With `--new`, an omitted
`-L`/`-S` connection allocates a unique socket so an existing default server is
never reused. Omit `--new` when the command attaches to an existing server.
`video` renders the composite client track; choose
`--renderer semantic|native`. Omit `--fps` to use the preset rate, or select
24, 30, or 60 FPS explicitly.

Hidden and detached panes continue their individual recording. The composite
track, like any terminal recording, exists only for the lifetime of the client
command.

## Pane recording model

The pane integration does not use `pipe-pane`. Termtrace is each recorded pane's
root process and owns an inner PTY for the real shell or command. It therefore
uses the same canonical recording path as `termtrace record`:

- exact PTY output bytes and timing;
- human input forwarded through the pane;
- terminal resize events and pixel dimensions;
- signal intent, result, and process exit;
- live and replayable semantic terminal state;
- terminal replies generated by the semantic engine;
- execution, environment, and durability provenance;
- the resolved Ghostty profile when available;
- stable tmux server, session, window, and pane identity.

No Ghostty window or GPU is needed during pane recording.

## Enable recording from tmux startup

Generate a fragment with the exact installed Termtrace path and secured state
directory:

```sh
mkdir -p ~/.config/termtrace
termtrace tmux config > ~/.config/termtrace/tmux.conf
```

Source it from `~/.tmux.conf`, before any configuration command that creates a
pane:

```tmux
source-file ~/.config/termtrace/tmux.conf
```

The next tmux server will record its initial pane and every later pane. A
server that is already running does not reread this file automatically.
Regenerate the fragment if the Termtrace executable moves.

The default output root is `$XDG_STATE_HOME/termtrace`, or
`$HOME/.local/state/termtrace` when `XDG_STATE_HOME` is unset. Recordings are
new owner-only directories below `sessions/`. Use `--output-root PATH` while
generating the fragment to select another secured root. Pane children inherit
the `TERM` value that tmux normally supplies, so recording does not change
terminal capability selection. `--term VALUE` provides an explicit override.

## Enable a running server

To begin recording all panes created from now on without restarting tmux:

```sh
termtrace tmux enable
termtrace tmux status
```

Existing panes remain alive but cannot be recorded retroactively. `enable`
reports their count, and `status` labels them `recorded=false`. They are
grandfathered only for their current root process. If an existing pane is
respawned after enable, the selected coverage policy applies to the replacement.

Select a non-default tmux server with the same connection forms as tmux:

```sh
termtrace tmux enable -L SOCKET_NAME
termtrace tmux status -S /path/to/socket --json
```

Disable the integration and restore the exact saved `default-command` with:

```sh
termtrace tmux disable
```

Disable does not stop or delete recordings that already completed.

## Select the recording scope

The default scope is every pane in the tmux server. You can instead select any
union of sessions, windows, and panes. For a generated startup configuration,
`--session` and `--window` are exact names evaluated when a pane process starts.
`--pane` is a stable pane ID:

```sh
termtrace tmux config --session work --session ops > ~/.config/termtrace/tmux.conf
termtrace tmux config --window editor --pane %7 > ~/.config/termtrace/tmux.conf
```

For a running server, `enable` and `scope` accept normal live tmux targets and
resolve them immediately to stable object IDs. Repeat selectors to combine
targets:

```sh
termtrace tmux enable --session work
termtrace tmux scope --session work --window work:logs --pane %7
termtrace tmux scope
termtrace tmux scope --all
```

Session scope records every new pane process in that stable session. Window
scope records every new pane process in that stable window. Pane scope records
the next process started in that stable pane. Renaming a selected session or
window after live target resolution does not change its scope.

A scope change never takes over a PTY that is already running. Current
recordings continue, and current excluded processes remain excluded. The new
scope applies when a new pane is created or an existing pane starts a new root
process. This boundary is necessary because Termtrace must own the child PTY
from process launch to capture full-fidelity evidence.

Use explicit-only scope when you want ordinary panes to run without recording:

```sh
termtrace tmux config --explicit-only > ~/.config/termtrace/tmux.conf
termtrace tmux scope --explicit-only
```

Then create one recorded pane with the saved default shell or command:

```sh
tmux new-window "$(tmux show-option -gv @termtrace-executable)" \
  tmux run --force
```

You can also start one recorded explicit command in any scope:

```sh
tmux new-window "$(tmux show-option -gv @termtrace-executable)" \
  tmux run -- htop
```

`--force` means “record the saved tmux default” even outside the selected
scope. An explicit command after `--` is always selected. Neither form can
attach retroactively to a command that is already running.

## Coverage policy

`warn` is the default. Creation hooks and the lightweight supervisor report an
uncovered selected pane without terminating it. This preserves the application
while making the coverage gap explicit in status and aggregate evidence.

Select `--coverage strict` only when the recording policy explicitly permits
Termtrace to close an uncovered selected pane after the startup grace period:

```sh
termtrace tmux config --coverage strict > ~/.config/termtrace/tmux.conf
termtrace tmux enable --coverage strict
```

Excluded processes run normally under either policy. The supervisor also
detects direct `respawn-pane` replacements in scope.

Ordinary tmux key bindings need no changes. If a command or plugin supplies an
explicit pane command, wrap it explicitly:

```sh
tmux new-window "$(tmux show-option -gv @termtrace-executable)" \
  tmux run -- htop
tmux split-window "$(tmux show-option -gv @termtrace-executable)" \
  tmux run --shell-command 'make && less build.log'
```

The first form preserves an exact executable and argument vector. The second
form deliberately uses `/bin/sh -c` for shell syntax. `termtrace tmux
status --json` is suitable for periodic coverage audits.

## Find and use recordings

While a pane is live, `termtrace tmux status` prints its canonical recording
directory. Managed recordings remain below the configured `sessions/` root
after panes close. Their `session.json` files include immutable `tmux_pane`
provenance, including stable IDs and launch-time names and indices.

Use a completed path with the normal Termtrace commands:

```sh
termtrace integrity verify SESSION --level content --json
termtrace analyze timeline SESSION
termtrace analyze index --session SESSION
termtrace artifact capture --session SESSION
```

The canonical event stream supports every normal semantic analysis and render
path. Native Ghostty capture uses the saved profile when one was available.
The default `--ghostty-profile auto` records without a profile when Ghostty is
not installed. Use `required` to fail pane startup instead, or `off` when only
semantic replay is needed.

## Fidelity boundary

The composite client track records the terminal screen produced by the outer
tmux client, so it includes status lines, borders, popups, copy-mode overlays,
layouts, and pane compositing. It is not a capture of the original Ghostty
framebuffer or monitor. Native video is a later replay through Ghostty and still
depends on external fonts, shaders, images, and other profile resources.

The aggregate manifest indexes observed session, window, and pane lifecycle;
layout; active window and pane; zoom; copy mode; pane moves; and pane-track
linkage. Changes shorter than the supervisor polling interval may not receive a
separate indexed transition. Tmux messages and prompts remain visible in the
composite track but are not separately indexed.

Coverage-gap history remains in the manifest after a gap resolves, with its
first observation, last observation, and resolution time. Matching lifecycle
events record when pane coverage gaps open and resolve.

Each pane track has the same fidelity as a normal Termtrace PTY recording. It
reconstructs the terminal states that the pane application produced, including
brief states and resizes, but it does not include tmux compositing. If a pane
closes, Termtrace records the received hangup, forwards it to the child, and
closes canonical pane evidence. A sudden power loss can leave incomplete but
integrity-checkable composite or pane prefixes, subject to the configured
durability window.

## Resource and data costs

Each live pane adds one Termtrace process, one inner PTY, an in-memory semantic
terminal state, and bounded I/O buffers. Each tmux server adds one small audit
process. CPU usage follows terminal output volume because bytes are parsed and
hashed once. Recording does not use the GPU; native rendering and video export
do.

Storage grows with exact terminal input, output, and event metadata. Quiet
shells are cheap; build logs and full-screen applications generate more data.
There is currently no automatic rotation, compression-after-completion, or
seven-day retention policy. Recordings contain everything typed or displayed,
including secrets, and remain until the user removes them or applies an
explicit registry garbage-collection policy.
